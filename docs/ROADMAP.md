当前里程碑验收：M1–M6 与 E1 已完成，正式交付版本0.3.1，最新交付记录见文末；下述“基线”和 R1–R9 表格保留最初审阅时的历史状态。

## 1. 项目定位与交付目标

把 weft 做成一个可嵌入、可复现的 **WebAssembly Component 部署计划编译器**：在执行前检查组件、类型和连线，并在 native / wasm-gc / js 上生成逐字节一致的计划。

优先用户是需要在本机、CI 或浏览器里检查组件组合的开发者。主要交付物是 MoonBit 规划库、CLI、版本化计划格式及可复现示例。原生运行适配器作为实验能力独立推进。

下一次稳定交付的用户路径：

1. 准备清单与组件文件。
2. 执行 `plan`，得到稳定计划或指向具体组件、端口、字段的错误。
3. 通过 `emit-wac` / `convert` 完成实际文件的往返，产物可以继续交给 `plan`。
4. 在浏览器中使用同一规划库检查相同输入并下载相同计划。

近期范围：同步函数、明确支持的值类型、DAG、离线规划。分布式调度、集群、热更新、durable execution、resource/async/stream/future 执行不进入本轮排期。

## 3. 代码审阅发现与优先级

以下结论来自当前源码；未执行的新反例应在对应任务中先固化为回归测试。

| 编号 | 优先级 | 当前证据 | 对应决策 |
|---|---|---|---|
| R1 | P0 | `scripts/check-backends.sh` 对测试管线使用 `|| true`，会吞掉测试失败 | 门禁必须传播退出码，保留失败日志 |
| R2 | P0 | `src/cli/runtime_native.mbt` 的 `run_plan` 只返回计划摘要；执行器的 `Bind` 分支调用端口查找，没有建立跨实例调用关系 | 明确区分规划成功与执行成功；真实执行单独设门禁 |
| R3 | P0 | 示例 reader 的 WAT 返回常数 0；sink 只有 import；CI 却在终点调用 `read`，且注释声称结果等于输入 | 重做有可观察结果的执行夹具，CI 必须断言结果 |
| R4 | P0 | CLI 的 `cmd_convert` 只接收名称和字节，将路径生成为 `<ns:name>.wasm` | 保留 `--dep` 的真实路径，并定义 `--out` 后相对路径基准 |
| R5 | P1 | `manifest_to_wac` 按清单数组顺序发射；名称消毒可能碰撞，字符串直接拼接 | 按依赖顺序发射；确定性名称映射；转义或明确拒绝无法表达的名称 |
| R6 | P1 | `check_wire_signatures` 仅比较展平后的 core 类型；`is_async` 未参与 `flatten_func` 检查 | 不能把 ABI 形状相同当作组件值类型兼容；明确拒绝超出支持范围的连接 |
| R7 | P1 | 规划器没有独立的目标 import 唯一提供方及未绑定 import 覆盖校验 | 定义完整部署计划与开放宿主依赖的区别，拒绝歧义绑定 |
| R8 | P1 | CLI 参数解析忽略部分未知/缺值参数；清单版本只检查 `0.1.` 前缀 | 参数和格式错误须在输入边界暴露 |
| R9 | P1 | 资源字段进入计划但执行器未落实；计划 hash 不包含组件二进制内容 | 写清配额与 hash 语义；不把元数据描述成执行保障或制品校验 |

## 4. 里程碑与验收

工期为一名熟悉 MoonBit 的开发者的有效工作日估算，不是日历承诺。先完成一个里程碑并验证，再更新下一阶段估算。

### M1：可靠性修复，v0.1.1（3–5 天）

目标：现有命令的成功、失败与文档承诺一致。

- [x] **M1.1 / R1**：删除吞错逻辑，日志过滤不改变测试退出状态；补 PowerShell 本地检查入口，与 Bash 脚本执行相同检查。
- [x] **M1.2 / R2、R3、R9**：修正文档、帮助与 CI 中的执行承诺。真正执行可用前，`run` 明确报未支持；计划摘要通过规划命令或单独的预览行为提供。类型检查与执行成功分别报告。
- [x] **M1.3 / R4**：转换入口保留依赖的包名、版本、路径、字节；定义默认输出及 `--out` 的路径基准。从其他工作目录运行也能读回产物。
- [x] **M1.4 / R8**：拒绝未知参数、缺值选项、额外位置参数、错误 `--dep` 与重复依赖；确定重复 `--out` 的拒绝策略。新增 CLI 测试，不只测试库函数。

验收门禁：

1. 在隔离测试夹具中故意让 `moon test` 失败，两个检查入口都返回非零，并显示原始错误。
2. 三后端全部原有测试继续通过，新增 CLI 用例通过，CLI 计划文件逐字节相同。
3. 用非默认文件名和带空格目录运行 `convert --out`，输出清单能直接运行 `plan`；相对路径及 Windows 路径行为有断言。
4. 不发生“只打印摘要却报告执行成功”；CI 的执行状态不依靠进程退出码单独判定。

### M2：连线与类型规则，v0.2.0（5–8 天）

目标：计划对支持范围内的输入具有明确的兼容性规则。

- [x] **M2.1 / R6**：先定义支持矩阵。同步标量要求类型匹配；record / tuple / list / option / result / variant / flags / enum 按明确的结构规则比较，遍历双方各自的类型表，不能直接比较 arena 索引。字段及 case 顺序纳入规则。复用上游可用的语义校验，ABI 展开继续作补充检查。
- [x] **M2.2 / R6**：对 async、resource、own/borrow、future/stream 等未支持语义给出 `Unsupported`，不因可以展平而放行。其他尚未实现的值类型也明确拒绝。
- [x] **M2.3 / R7**：定义 wire 唯一性；同一目标 import 有多个提供方时报错。未绑定 import 默认阻断完整部署计划；若支持宿主 import，必须显式声明并写入计划。接口内函数不能被误当作已满足整个接口实例的绑定。
- [x] **M2.4 / R5**：WAC 发射复用独立的图排序逻辑，避免让适配层反向耦合 CLI；处理逆序清单、环、命名碰撞、保留字、引号、换行及接口路径。无法保真表达的结构返回具名错误。
- [x] **M2.5 / R8、R9**：固定清单和计划 schema、版本接受规则、排序、编码、换行、hash 输入范围。新增字段或改变兼容性策略时按版本发布；保留旧版黄金样本。

验收门禁：

1. `bool` 与 `u32`、不同语义结构但相同 ABI 形状的连线被拒绝；语义相同但类型表索引不同的连接通过。
2. 输入组件和 wires 的排列变化不改变计划；Unicode 名称、转义字符和较大整数边界在三个后端结果一致。
3. 重复绑定、未绑定 import、未支持异步/资源语义有稳定错误，指出组件与端口。
4. 逆序清单发射的 WAC 能由现有验证器检查；往返保持组件与连接语义，不静默丢字段。
5. 对不能携带的资源策略明确报错或提示不保留；不宣称 WAC 往返保留了其无法表达的配额语义。

### M3：可嵌入 API 与浏览器演示，v0.3.0（4–6 天）

目标：把已有跨后端能力交付给真实使用者。

- [x] **M3.1**：提供无文件系统依赖的规划入口，接收清单字符串和按组件名索引的字节；输出计划或结构化诊断。现有包继续保持单向依赖。
- [x] **M3.2**：提供最小浏览器演示：本地选择清单和组件 → 检查 → 展示依赖图与错误 → 下载规范计划。通过内存中的逻辑路径匹配组件，不要求浏览器访问原始本地绝对路径。
- [x] **M3.3**：加入成功链、分支汇合、成环、类型不符、缺失导入五类示例。图展示来自实际计划，不复制另一套排序算法。
- [x] **M3.4**：固定发布验证的 MoonBit 工具链版本，记录依赖版本；生成 CLI 制品、校验和、版本信息和库消费者示例，完成一次干净环境安装验证。

验收门禁：浏览器使用相同输入下载的计划与 CLI 文件字节一致；所有组件在本地处理；外部 MoonBit 消费者能独立引入规划 API；从空目录按 README 完成首次使用。

这条支线依赖 M1 的门禁与 M2 的语义规则，不作为规划库发布的前提。

- [x] **E1.1 / R2、R3**：确认 wasmoon 能否在实例化时把源 export 安装为目标 import；在 Linux 建立最小两组件探针，记录实际 API 与失败条件。

- [x] **E1.3 / R2、R9**：若探针成功，再设计按拓扑序准备 import 后实例化的执行过程，修订当前“全部实例化后再 Bind”的轨迹；按需调整调用目标模型、非零退出码与参数验证。

## 5. 格式与架构决策

1. **保持纯核心**：`manifest`、`ir`、`plan`、`wac_adapter`、`exec_plan` 不引入运行时、网络或文件系统。CLI 与浏览器负责 I/O。
2. **区分规划与制品完整性**：现有 FNV `plan_hash` 只标识规范计划体。同路径组件内容改变而接口不变时，hash 可能不变；不用于安全校验。若出现锁定部署制品的需求，再引入组件摘要和新计划版本。
3. **诊断逐步结构化**：稳定错误码 + 消息 + 组件/端口/字段位置；先沿用现有错误类型，统一边界，避免一次重写所有模块。
4. **确定性定义具体化**：对输入顺序置换不敏感；对路径文本等未归一化内容按格式约定处理。随机测试采用固定种子，可复现失败。
5. **性能先测后改**：当前排序实现继续使用。补 100 / 1,000 组件的链、扇出和扇入基线；出现测量瓶颈后再考虑堆、缓存或增量规划。

## 6. 每次变更的交付标准

- 正确性修复先提供能复现问题的用例；文档调整不另写实现镜像测试。
- 纯逻辑变更通过三后端测试；涉及 I/O、路径或命令参数时再增加 CLI 集成验证。
- 计划格式变更检查黄金字节与迁移说明；API 变更更新 `moon info` 生成接口。
- 执行相关变更在支持平台验证真实结果；本地无法运行时明确标记未验证，不用类型检查替代。
- README 的每项核心承诺都能指向测试、示例或明确限制。

## 7. 建议开发顺序

第一批：M1.1 门禁退出码 → M1.2 能力与文档对齐 → M1.3 转换路径 → M1.4 参数校验。

第二批：M2.1/M2.2 类型规则 → M2.3 绑定覆盖 → M2.4 WAC 保真 → M2.5 格式契约。

第三批：M3.1 API → M3.2/M3.3 浏览器示例 → M3.4 发布验证。

E1 在 M1 后做限时探针，成功后另行估算执行器实现；不承诺在规划版本工期内完成。M1–M3 合计约 12–19 个有效工作日，每阶段以验收结果决定是否发布。
