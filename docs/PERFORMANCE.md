# 规划器规模基线

按 ROADMAP.md 第5节先测量，再决定是否优化。使用真实组件二进制和实际 CLI，
覆盖总计100、1,000个组件的链、扇出与扇入，每种均有 N−1 条 wire，所有 import 均完整绑定。
扇入末端有 N−1 个独立函数 import；各组件字节会按实际 CLI 路径重复读取、解码，不预先缓存接口。

在仓库根目录启用 release/README.md 的固定工具链后运行：

```bash
node scripts/benchmark-planner.mjs 3
```

需要 Node、MoonBit 与 native C 编译环境，不依赖 wasmoon 执行器。夹具生成、三个后端的 debug
构建不计时。每场景/后端先作一次不计时预热，再对全新 CLI 进程采样3次，保留原始毫秒值、最小值、中位数。
每个计时样本包括进程启动、文件读取、组件解码、语义校验、图算法和 JSON 输出写入。
OS 文件缓存通常已热；这不是纯拓扑排序基准，也不是完全冷启动磁盘测试，不用于宣称执行器吞吐。

每次检查实例数、完整 wire 集合及拓扑先后关系；三个后端输出必须逐字节一致。
每个计时样本也核对字节，再额外反转 components/wires 输入验证确定性。
异常、非零退出、单次超过120秒或结果不符会使脚本失败，不输出成功报告。

报告输出 `_build/benchmarks/latest.json`，记录提交、脚本 SHA-256、工具链、debug 构建模式、
OS/CPU/Node、全部原始样本与每场景规范计划的 SHA-256。
CI 的 `planner scale baseline (linux)` job 同样采样3次，并上传 `planner-scale-baseline` artifact。
没有绝对毫秒性能门槛；runner 共享负载与平台差异较大，应在相同环境多轮测量后比较。

阶段测量现已加入同一脚本，当前报告为schema_version 3；类型成本探针方法见文末，历史报告保留原版本。

## 扇出拓扑排序优化（2026-11-09）

增加 graph_build_ms / cycle_check_ms / topo_ms 三项独立细项计时，graph_probe_ms 仍包括整个图路径。
固定Windows工作负载的优化前采样显示：千组件扇出 native 拓扑排序约93ms，明显高于图构建约4ms与环检测约0.1ms。
检查实现确认旧ready数组每次插入线性扫描，出队从头部移除，宽ready集合会产生二次开销。

改用固定core的priority_queue（最大堆），以负节点下标为键实现最小就绪节点优先。
build_graph 按项目Unicode字典序排列节点，因此下标次序与原先的名称排序一致。
就绪队列的操作改为O(log V)，不改变环检测、wire排序、hash或计划格式。
Graph调用者仍须遵守已公开的nodes按字典序排序契约。

新增3个图测试：两组各1,024个五节点DAG与独立扫描参考算法对照，含Unicode/前缀名称与动态释放较小节点；
千节点宽ready集合；空图与带环图部分进度。优化前先在旧实现固化对照，优化后三后端均通过。
全量门禁已纳入graph包，三后端各134个测试、33项CLI检查与独立消费者通过。
最终性能复测与Linux CI均通过；原有记录保留，不将单项排序提速等同于整个CLI提速。

## 扇入绑定覆盖优化（2026-11-09）

继续定位非图路径，使用 [MoonBit white-box benchmark](https://docs.moonbitlang.com/en/latest/language/benchmarks.html)
直接比较生产 check_bindings 与测试中保留的旧扫描参考实现。夹具为合法的source→sink多import计划，
不计组件解码/端口类型解析；100与1,000个import分别测量，使用b.keep保留结果，count=3，由框架自动校准批次。

```bash
moon bench src/plan --target native --debug
# 也可替换为 wasm-gc / js
```

旧实现为每个已排序名称重复遍历import表，并线性检查不可连线名称。新实现构造带原始序号的端口描述符，
一次按名称/序号排序后顺序检查，避免平方次扫描；相同名称的不可连线项优先，重复import保留原始先后。
覆盖检查复杂度由宽表上的O(I²)扫描改为O(I log I)排序加遍历，不改变重复提供方的优先诊断。

先在旧实现固化千import完整/漏绑、重复端口、函数/实例混合、不可连线名称等对照用例，再改生产实现。
不通过Map覆盖重复端口，不扩大公共IR可接受范围。原生产规划API与计划格式不变。

初测千import native直接检查约5.1→2.9ms，改善的是绑定覆盖子步骤，不能解释成整条CLI提速；
端口解析及类型展开仍可能占据其余开销。最终本机三后端各136回归测试、33项CLI检查与独立消费者通过，18场景优化前后计划SHA全部一致。
CI在规模基准后顺序运行三后端的直接benchmark，文本结果随planner-scale-baseline制品上传。

## 宽端口表的规划内索引（2026-11-09）

千import批次的旧端口解析基准在本机native约106ms，远高于此前绑定覆盖检查约5ms。
每条wire反复扫描同一表是扇入的主要候选热点。新增白盒batch基准保留旧解析器，
同批次构造IR并查询全部端口；索引版本计入构造成本，使用结果校验和防止工作被优化掉。

生产plan现在为至少16项的宽import/export表按需构造索引，限于单次plan调用，
小表仍使用线性路径以减少逐组件Map分配。16是保守的小表启发式，不宣称最优阈值。
索引键含清单组件名和import/export方向，重复名称保留原表第一项，嵌套接口函数仍按原路径查找。
公有resolve_port保留线性行为，不修改公共签名或计划格式。

新增三项普通对照测试：1/15/16/100/1000端口批次、重复端口/Unicode接口路径/错误信息、
公共IR改动后第二次规划重新建索引。小表、宽表、两侧及旧参考结果均核对。
本机三后端各139测试与33项CLI检查、独立消费者通过，18场景优化前后计划SHA全部相同。
未引入跨规划或全局缓存，不对类型展开额外缓存；其余开销继续用数据判断。

## 发布后类型成本复测（2026-11-10，报告schema_version 3）

按M9重新运行当前生产源码的18场景，再在独立profile_planner中增加两项重叠探针，
不修改ir/plan生产实现、公有API或计划格式。仍使用100/1,000组件及每项3次采样，不扩展到10,000组件。

| 新字段 | 范围 |
|---|---|
| `type_table_probe_ms` | 按每条wire的两端逐次调用现有`ir.to_model_table`，包括结果保活和条目计数 |
| `flatten_probe_ms` | 同批已解析端点逐次调用现有`ir.flatten_func`，包含其内部类型表转换、canonical ABI展开、结果保活和展开值计数 |
| `endpoint_count` | 实际探测端点数，须等于wire数量的两倍 |
| `type_table_entries` | 所有逐端点转换结果的表长之和，须与输入类型表的表长之和相同 |
| `flat_value_count` | 展开参数/结果总数，须与实际CLI输出中两端规范签名的值数量一致 |

端口解析在探针计时之外完成；`bench.keep`保留计算结果，避免只读取长度时计算被消除。
每轮仍验证完整计划字节、wire集合、拓扑关系及反序输入，测量工作量另行断言。
两项探针都与规划工作重叠，且互相重叠，不能相加到流水线耗时，也不能相减后声称得到了精确ABI耗时。
探针在同进程各轮末尾额外分配对象，可能影响后续GC与JIT；不将新旧测量工具的流水线耗时变化当作优化收益。
