# weft 核心深化规划

日期：2026-11-12。源码审阅基线：`fd4b92d`；正式发布基线：0.3.1。以下全部是拟开发内容，不代表已经实现。

## 1. 重新确定技术目标

下一阶段把 weft 从函数连线规划器推进为**可验证的 WebAssembly 组件组合编译器**：针对明确支持的组件模型子集，检查完整接口绑定，将计划绑定到具体组件内容，并支持在另一宿主独立核验和执行。

用户要解决的具体问题是：“我在浏览器或CI里审核过这份组合，Linux上实际启动的是否仍是同一批组件、同一组接口和同一份连接关系？”

核心交付围绕两项能力：

1. **接口组合正确性**：从函数粒度提升到接口实例粒度，完整检查消费者要求的成员与类型关系，给出具体失败路径。
2. **计划与制品一致性**：独立校验计划引用的组件字节、绑定、类型及依赖顺序，拒绝二进制替换和计划篡改。

工程维护继续保留，但文档数量、微基准提速和UI扩展不再作为本轮技术成果的主体。暂不扩展分布式、热更新、通用运行时、资源沙箱或全量组件模型。

## 2. 当前限制与应形成的新成果

| 当前实现 | 技术缺口 | 本轮成果 |
|---|---|---|
| `Port::Interface`保留名称和函数列表，消费者的接口实例import被拒绝 | 函数都存在并不等于接口实例已正确绑定；命名类型与别名关系不能靠路径拼接表达 | 保留类型导出与引用关系的IR、实例级绑定规则与检查器 |
| 严格函数结构比较及ABI展开 | 暂无接口作用域内的类型对应关系 | 按消费者接口要求建立跨组件类型映射，输出成员级诊断 |
| 计划保存路径、顺序、wire与FNV标识 | 同路径组件内容可变化，现有hash不能标识部署制品 | 版本化组件摘要、输入锁和计划校验协议 |
| 规划器同时生产顺序和JSON | 重新执行同一生成器不足以独立检查外部计划 | 以不变量为中心的校验入口及有意篡改用例 |
| 自有黄金测试及少量真实执行 | 同一实现的遗漏可能同时存在于生成和测试夹具 | 生成式测试、外部组合验证及结果断言 |

## 3. D0：规则与可行性探针（2–3个有效工作日）

先用最小反例确定边界，随后再修改格式和公共接口。

- [x] 固定本轮采用的Component Model文档快照和上游依赖版本，记录支持规则；不把最新规范中的全部特性当成现有依赖已支持。
- [x] 制作真实组件：一个导出两个同步标量函数的接口实例，一个导入该实例的消费者。检查语义解码是否保留函数、命名类型、alias以及类型导出；记录当前IR丢失的信息。
- [x] 在Linux以现有linker验证安装完整实例再实例化消费者；消费者必须实际调用两个函数。成功、缺成员、错误类型与错接另一提供方都有结果断言。
- [x] 选定一个能在三后端运行的SHA-256实现，核对许可证、标准测试向量、空输入和二进制字节处理。摘要计算留在纯逻辑层，不为跨后端兼容自行发明密码算法。
- [x] 固定一种外部WAC组合/验证工具及其版本，用最小组件确认接口实例传递和失败信息；先证明命令能复现，再列为后续门禁。

输出：接口规则短文、四类二进制夹具、真实执行探针、摘要与外部工具选择记录。
若上游不能提供完整命名类型关系，先实现保留该信息的解码适配或限缩支持范围；不能退化为“比较函数列表后宣称支持接口”。若运行时探针失败，静态规划可继续，但执行成果单列阻塞与退出条件。

## 4. D1：接口实例级组合，候选v0.4（8–12天）

### 模型与算法

- [x] 引入明确的绑定种类：旧函数wire保持原语义；新实例绑定使用结构化端点，避免靠点号猜测函数与实例。定义重复、冲突及函数/实例混用的拒绝规则。
- [x] 扩展IR保存实例成员、命名值类型、导出类型和alias关系；公开IR兼容性变更要有迁移说明。旧的函数接口不得静默丢弃新信息。
- [x] 建立消费者类型引用到提供方类型引用的局部对应表。比较时按两侧各自作用域解析引用，用已访问的类型对控制遍历；非法循环引用返回错误，不能把遇到已访问节点直接当作兼容。
- [x] 首轮支持同步、无resource的接口及现有可支持值类型。提供方必须满足消费者全部要求；是否允许额外导出、参数名和字段顺序如何比较，依据固定规则明确规定。不得把此子集称为完整subtyping。
- [x] 保证接口级绑定覆盖全部消费成员；混合绑定一个成员不能被当作满足整个实例。缺成员、类型冲突、未支持成员均报完整路径。
- [x] 将实例绑定降到明确的执行操作及WAC发射，统一规划语义；展示层读取同一计划，不另外推导绑定关系。

### 验收

1. 实例级两函数调用在Linux实际通过；断线失败，错接不同提供方改变结果。执行支持限于D0确认的调用类型，不扩大为任意复合值执行。
2. 同义类型使用不同arena索引或alias链时正确匹配；同ABI但不同语义类型、缺成员和重复绑定被拒绝。
3. 覆盖嵌套复合值、函数/实例混合冲突、未支持resource和async，诊断点名组件、接口和成员。
4. 原有函数计划保持旧模式行为；新格式显式版本化，三后端输出逐字节一致。外部验证器接受支持子集的有效WAC，并拒绝约定的反例。

resource身份、own/borrow、完整WASI接口和async另行设计。接口名称相同、结构相同或摘要相同均不能自动证明resource身份相同。

## 5. D2：绑定制品的计划与独立校验，候选v0.5（6–9天）

### 格式和API

- [ ] 定义新的部署计划格式：声明受支持的语义profile、格式版本、规划器版本；每个实例引用的制品包含明确算法的字节摘要和长度。输入由宿主以逻辑ID提供，不强制写本机绝对路径。
- [ ] 定义锁文件内容及规范编码：组件字节摘要、规范清单/绑定意图、语义profile和版本。锁文件用于固定已审核输入；额外文件、缺少文件、重复ID、未知算法的处理必须明确。
- [ ] 分清三类标识：旧FNV计划标识、组件内容摘要、新计划摘要。定义摘要覆盖的精确字节和自引用字段排除方式；改变组件内容即使接口不变，也应改变新部署标识。
- [ ] 提供纯API `verify`：接收计划文本、锁定输入与组件字节映射，返回结构化校验结果。独立解析计划，不信任其中的order、incoming、签名或摘要；拒绝重复JSON键和非法索引。
- [ ] 校验器核对摘要、实例集合、锁定的绑定意图、端口类型、每个import的唯一覆盖、DAG及顺序。可以复用解码和类型基础函数，但不能只调用compile再比较文本作为唯一实现。
- [ ] 区分“计划有效”和“规范计划”：任一合法拓扑序可满足有效性；仅生成器规定的字典序与编码满足规范性。CLI分别输出校验失败和非规范结果，不混为类型错误。
- [ ] CLI增加计划核验入口；实验执行器在实例化之前核验锁定输入，摘要或绑定意图不符则不执行。浏览器可导出计划与锁文件。

### 必须通过的反例

替换同路径同接口但行为不同的组件；修改wire指向另一类型兼容提供方；删除绑定；重复目标；伪造类型签名；篡改order/incoming；伪造摘要；跨格式和未知profile；有效但非规范拓扑序。

其中“改接另一兼容提供方”可能仍是一个语义有效的新计划，必须通过锁定绑定意图区分其是否为原审核结果。仅检查类型与DAG不能检测这种变更。

验收：离线核验可在三后端完成；换一个目录仍可核验同一组字节；同输入重排生成同一规范结果；执行器在失败核验后没有实例化。摘要保证相对于可信输入的内容一致性，**不提供作者身份、签名信任或恶意组件隔离保证**。

## 6. D3：组合正确性证据与真实案例（5–8天）

- [ ] 编写带固定种子的生成器，生成支持子集内的类型图、接口、DAG及有效绑定，再施加单点变异构造反例。初始每次CI使用有时间/内存上限的约2000个小案例，依据覆盖和耗时调整，不能只追求案例数。
- [ ] 检查变形性质：清单/绑定排列不影响规范结果；arena重编号和合法alias替换不影响兼容结论；删除必要成员导致失败；相同SHA对应的逻辑路径迁移按格式规则处理。
- [ ] 将有效输入降到固定外部验证器进行差分；只比较共同支持的语义范围。失败时保存种子、原始输入、工具版本及最小反例；工具拒绝超出范围的输入不算weft缺陷，也不能计作通过。
- [ ] 对生成计划作系统性字段变异，覆盖D2每项不变量；提供一个简单参考验证流程与生产校验器对照，防止生成器和校验器共享同一遗漏。
- [ ] 制作完整离线示例：两个可切换的计算提供方、一个经接口调用的消费者；浏览器/CI生成并审核计划，Linux核验后运行。两个函数均参与可断言计算，不能由宿主代算结果。
- [ ] 演示替换组件内容、改接wire、缺接口成员三个失败，以及合法更换提供方后重新生成锁和计划的成功。复合值静态检查另有例子，不将标量执行演示包装成全部类型可运行。

验收交付：可复现实例、生成/变异/差分报告、失败样本缩减方法、三后端一致性证据和真实调用断言。这里提供可检查的不变量与测试证据，不声称已完成形式化证明。

## 7. 架构与版本约束

- `ir`负责保留语义；独立类型比较层处理作用域和引用对应；`plan`生成组合，新增核验层检查输入与计划，宿主适配器执行；全部纯层不引入文件系统或wasmoon。
- SHA和格式校验须复用经过验证的基础实现；执行linker不是类型检查的替代品。
- 不在0.3.1上原地更改公开计划格式；新模式显式选择，旧黄金样本和旧消费者继续回归。模块版本、清单版本、计划版本分别说明，不能统一改号了事。
- 新增实例导入必须保持默认拒绝未声明宿主能力；不得为了运行例子默认安装文件系统、网络等host imports。
- 主动工作总量初估21–32天，外部API或解码适配不确定性在D0后重新估算。每个阶段以验收决定是否发布，不承诺一次覆盖所有组件模型能力。

## 8. 执行优先级与阶段决策

**先D0 → D1 → D2 → D3。** D1过程中可先搭建D3最小参考夹具；D2开发时同步做计划变异用例，不把全部验证推到最后。

第一批只做三个探针：完整实例解码、Linux实例import实际调用、跨后端SHA。三项结果和支持规则清楚后，才批准具体IR与格式设计进入实现；这里的阶段检查属于开发判断，不新增用户确认流程。

若工期只能完成一个版本，优先交付D1完整接口实例组合及一份真实执行案例，再交付D2制品一致性；不拆成大量只有接口、缺实际语义的空版本。性能只在新算法出现测量瓶颈后处理。

### D1阶段判断

上游已保留所需语义，不需要更换依赖或实现新的二进制解析器；下一步先实现独立的作用域IR解码适配，
保留实例成员、类型导出和alias边，再建立消费者到提供方的局部类型对应。旧函数模式及其公开IR继续回归。
新模式的结构化实例端点、冲突/覆盖规则和版本迁移须一并实现，不能只给现有函数列表增加“实例兼容”标记。
当前运行时对缺成员仅报告外层ops，D1必须先由静态检查提供成员级诊断。
